# OOH Campaign Performance Analyzer

Out-of-home advertising campaign analytics. It finds under-delivering advertising
inventory **continuously**, not at end of campaign the way agencies normally catch
it by hand during reconciliation.

## Context

This is a **portfolio project**. The owner is a first-year Honours Mathematics and
Business Administration (Co-op) student at the University of Waterloo, and spent
five months inside a WPP/GroupM out-of-home agency watching that reconciliation
happen manually. The job of this code is to be **defensible line by line in an
interview** — not to look impressive at the cost of being explainable.

## Non-negotiable constraints for all future work

- **Synthetic data only.** All data is generated by `src/generate_data.py` with a
  fixed random seed (42). Never introduce real agency or client data. Never remove
  the on-page or in-README notice that the data is synthetic.
- **Assumptions stay documented.** Every modelling assumption lives in
  `docs/assumptions.md`. If you add a metric that rests on an assumption, document
  it in the same change.
- **Boring over clever.** Prefer the readable implementation. This code gets
  explained out loud under questioning.
- **Small steps.** Do not write more than ~150 lines in one go without stopping to
  explain it.
- **Python computes, the browser renders.** Metrics are computed in Python and
  exported to `public/data.js` / `public/data.json`. Do not move any calculation
  into JavaScript. `public/app.js` is presentation only.

## Architecture

```
src/generate_data.py   synthetic data -> SQLite (data/ooh.db), fixed seed
src/schema.sql         4 normalized tables, enforced foreign keys
src/metrics.py         delivery variance, CPM, rate efficiency, GRP, reach/frequency
                       each function takes a DataFrame, returns a DataFrame, does one thing
src/export_json.py     loads the DB, runs metrics.py, writes public/data.json AND public/data.js
src/queries.sql        standalone analytical SQL (CTEs, ROW_NUMBER/LAG window functions)
public/                static dashboard: index.html + style.css + app.js + data.js
tests/test_metrics.py  unit tests on hand-verifiable inputs (pytest)
docs/assumptions.md    every modelling assumption, written down
```

Data flow: `generate_data.py` -> `data/ooh.db` -> `export_json.py` (via `metrics.py`)
-> `public/data.{json,js}` -> browser. One source of truth for every number, and the
figures on screen are the ones the tests cover.

`data.js` exists because browsers block `fetch()` on `file://` URLs; it assigns
`window.OOH_DATA` so the dashboard opens straight from disk. `data.json` is the same
payload for anything that prefers a fetch.

## Data model (4 tables)

| Table | Holds |
|---|---|
| `sites` | Inventory: city, area, format, size, daily traffic, rate card |
| `campaigns` | Client, industry, objective, flight dates, budget |
| `placements` | campaign x site x date window, negotiated rate, contracted impressions |
| `delivery` | Per placement per day: estimated impressions, verified impressions, downtime hours |

## Rebuild the data and dashboard

Python 3.10+. From this directory:

```bash
pip install -r requirements.txt      # pandas, pytest
python src/generate_data.py          # builds data/ooh.db
python src/export_json.py            # writes public/data.json and public/data.js
python -m pytest tests/ -q           # 10 tests
cd public && python -m http.server 8000   # view locally
```

If SQLite can't take file locks (network drives, some mounts), point the DB at a
local path: `OOH_DB=/tmp/ooh.db python src/generate_data.py` (also honoured by
`export_json.py`).
